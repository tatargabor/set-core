# Spec-Verify Gate — what `/opsx:verify` must do beyond the stock skill

**Read this whenever you run `/opsx:verify`.** The orchestrator's spec-verify gate parses
this file's sentinels; the checks below are the ones the framework relies on and the stock
skill does not perform.

**Why this lives here and not in the skill, stated because the answer is not obvious and
the mistake is cheap to repeat.** `.claude/skills/openspec-*/SKILL.md` and
`.claude/commands/opsx/*.md` are **generated by the `openspec` CLI**. Every `openspec
update` rewrites them wholesale — there is no preserve marker, no merge, no per-file
opt-out. Anything framework-specific written into them survives until the next CLI upgrade
and then vanishes silently, which is exactly what happened on 2026-08-17: an `openspec
update` from 1.1.1 to 1.9.0 removed the sentinel instructions the gate depends on, and the
only thing that noticed was a unit test. So the rule is:

- **OpenSpec-native concepts** (scope boundaries, `[REQ: …]` tags, acceptance criteria,
  per-artifact guidance) belong in `openspec/schemas/<name>/schema.yaml` and
  `openspec/config.yaml` — the CLI's own extension points, which `openspec update` does
  not touch.
- **Framework concepts** (this gate, its sentinels, orchestration inputs) belong in a
  framework-owned file like this one.
- **Never edit a generated skill or command file.** It reads like the right place and it
  is the one place the edit cannot survive.

## The two sentinels — the gate's actual input

**End the verification report with BOTH sentinels**, in this order, as the final TWO lines
— each on a line of its own, with nothing else on the line (no quoting, no trailing
comment):

```
CRITICAL_COUNT: <integer count of CRITICAL-severity findings, 0 if none>
VERIFY_RESULT: PASS|FAIL
```

- `VERIFY_RESULT: PASS` — if no CRITICAL issues; `FAIL` — if any exist.
- `CRITICAL_COUNT` counts ONLY findings marked CRITICAL. WARNING and SUGGESTION do not
  count — emit `0` if those are all you have.

**Why the count is not optional.** The orchestrator downgrades `VERIFY_RESULT: FAIL` +
`CRITICAL_COUNT: 0` to a pass, so warning-level findings report without blocking the merge.
Omit the count and the gate blocks and retries — the *safe* direction, but it means an
agent following the stock skill exactly could never produce the one input that mechanism
needs. A guard is only as good as the document that teaches its input.

**Nothing else on the line, and a bare number after the colon.** Both parsers require the
whole line to be the sentinel: `CRITICAL_COUNT: 0 — but I could not check the auth module`
and `VERIFY_RESULT: PASS is NOT what I emit here` were each read as their opposite before
that was tightened. If you need to qualify a verdict, do it in the body above, never on
the sentinel line.

## Completeness checks the stock skill omits

**Acceptance Criteria checking**:
- Parse the `## Acceptance Criteria (from spec scenarios)` section from tasks.md (if present)
- Find all `AC-N:` items and check their checkbox status
- If unchecked AC items exist:
  - Add CRITICAL issue: "Acceptance criterion not met: <AC description>"
  - Include the source `[REQ: ..., scenario: ...]` reference in the recommendation
- If all AC items are checked: note "Acceptance Criteria: N/N passed"
- If the section is absent: note "No acceptance criteria section — skipping AC check" (not an error)
- Exclude AC items from the plain task count, so a report cannot double-count them

**Traceability Matrix**:
- Parse `[REQ: <name>]` tags from all implementation tasks in tasks.md (case-insensitive, whitespace-tolerant)
- Extract all `### Requirement:` headers from the change's delta specs
- Build and output a traceability matrix under the summary scorecard:

  ```
  ## Traceability Matrix
  | Requirement | Tasks | Status |
  |-------------|-------|--------|
  | req-name    | 1.1, 1.3 | Covered |
  | other-req   | (none) | MISSING |
  ```

- For each requirement with no matching task: add CRITICAL "Requirement not covered by any task: <name>"
- For each `[REQ: <name>]` tag matching no spec requirement: add WARNING "Unresolved requirement reference: <name>"
- For each task without any `[REQ: ...]` tag: add WARNING "Task without requirement link: <task description>"
- If no delta specs exist: skip the matrix, note "No delta specs — skipping traceability check"

## Coherence checks the stock skill omits

**Scope Boundary Enforcement**:
- For each delta spec, check for `## IN SCOPE` and `## OUT OF SCOPE` sections
- If both are absent for a spec: note "No scope boundary defined for <spec> — skipping scope check"
- If OUT OF SCOPE exists: check the implementation (diff or codebase) for evidence of
  implementing those items. If found, add WARNING "Out-of-scope implementation detected:
  <item>" with the recommendation "Remove <item> or update spec scope boundary"
- If IN SCOPE exists: check that its items have implementation evidence, and note them as
  covered in the report

**Overshoot Detection** (runs after the scope boundary check):
- If no delta specs exist: note "No delta specs — overshoot check skipped" and skip
- Diff the change branch against its merge-base (`git diff $(git merge-base HEAD main)..HEAD`
  or equivalent)
- Scan the diff for new routes, endpoints, components, exports, and database tables
- For each new item, check whether it corresponds to a requirement in the delta specs (by
  name or IN SCOPE entry); if IN SCOPE is absent, fall back to requirement names only
- Use judgment to distinguish implementation details (helper functions, utilities serving a
  spec requirement) from new user-facing features — do NOT flag internal helpers
- If untraced: add WARNING "Potential overshoot — new <route/component/export> not in spec:
  <item>", recommending "Remove <item> or add a spec requirement for it"
- Overshoot severity is always WARNING, never CRITICAL
- Add the note: "Overshoot detection uses heuristics — review flagged items manually"

**Change-Specific Verify Hook**:
- If `<change-dir>/verify-hook.sh` exists, run it: `bash <change-dir>/verify-hook.sh`
- The hook owns any repository-wide gate the change wants to enforce (e.g. hardcoded-path
  audit, migration residuals, schema consistency)
- A non-zero exit adds a CRITICAL issue: "Change-specific verify gate failed — see stderr above"
- Recommendation: "Fix the residuals the hook reported, re-run the hook, then retry /opsx:verify"
- Absence is not an error — the hook is opt-in per change

## Report shape

The summary scorecard carries the extra columns these checks produce:

```
### Summary
| Dimension    | Status                          |
|--------------|---------------------------------|
| Completeness | X/Y tasks, N/M ACs, traceability|
| Correctness  | M/N reqs covered                |
| Coherence    | Followed/Issues                 |
```

Severity assignment:

- **CRITICAL** — incomplete tasks, unchecked acceptance criteria, requirements with no task
  coverage, missing requirement implementations, a failing verify hook
- **WARNING** — spec/design divergences, missing scenario coverage, unresolved REQ tags,
  tasks without REQ tags, out-of-scope implementations, overshoot detections
- **SUGGESTION** — pattern inconsistencies, minor improvements

When uncertain, prefer SUGGESTION over WARNING and WARNING over CRITICAL — the count drives
a merge decision. Every issue needs a specific recommendation with `file.ts:123`-style
references where applicable.

**Graceful degradation** — always state which checks were skipped and why:

- Only tasks.md: verify task completion, skip spec/design/traceability checks
- Tasks + specs: completeness (including traceability) and correctness, skip design
- Full artifacts: all three dimensions including overshoot
